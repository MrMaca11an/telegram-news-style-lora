# RESULTS: адаптация двух Telegram-стилей новостей (type1 `@banki_oil`, type2 `@moscowach`)

Базовая модель `unsloth/Qwen3.5-2B` (BF16), два LoRA-адаптера (r=16, alpha=16, все attention/MLP-проекции, ~10.9M обучаемых параметров = 0.49%), обучение через Unsloth + TRL SFT (`completion_only_loss=True`), жадное декодирование. Все числа ниже измерены; ничего не додумано.

## 1. Дисциплина работы с данными

- По 25 исходных пар на стиль → фиксированное разбиение: 20 train / 5 validation. Синтетические пары (20 на стиль) существуют как варианты `mix10`/`mix20`; validation везде один и тот же.
- 5 тестовых новостей (`data/raw/test_inputs.jsonl`, id 1–5, sha256 `2e7449ff…`) не использовались в обучении и не использовались для подбора гиперпараметров. Полное раскрытие: после первой тестовой генерации (предыдущий запуск), показавшей уход в многословность при `max_new_tokens=512`, лимит генерации установлен на 256 токенов — это осознанный выбор с учётом теста, сделанный один раз; адаптеры/промпты по метрикам теста НЕ выбирались (только validation).
- Ключевой факт распределения, найденный при аудите: входы validation — 356–565 знаков; входы теста — 854–951 знаков — вне диапазона обучающих входов (180–585). Этот OOD-разрыв объясняет, почему более ранний адаптер `type2_orig` проходил validation 5/5, но коллапсировал на тесте (1/5): дословное копирование источника, лишние абзацы.

## 2. Выбор метода (одинаковая validation, измерено)

Формат / эвристические числовые флаги на одних и тех же 5 validation-примерах (детали: `reports/validation_comparison.md`):

| стиль | метод | формат | val loss | примечание |
|---|---|---|---|---|
| type1 | наивный baseline-промпт | 0/5 | — | Markdown, списки, эмодзи |
| type1 | zero-shot спека стиля | 0/5 | — | нестабильно |
| type1 | few-shot (3 пары) | 5/5 | — | теряет числа |
| type1 | LoRA `type1_orig` | 5/5 | 1.996 | грамматический брак в 1/5 |
| **type1** | **LoRA `type1_mix10` (выбран)** | **5/5** | **1.966** | лучший val loss, одна малая дефект-деталь |
| type2 | наивный baseline / zero-shot | 0/5 / 3/5 | — | — |
| type2 | few-shot | 5/5 | — | силён только на коротких входах validation |
| type2 | LoRA `type2_orig` | 5/5 | 1.399 | коллапс на длинных тестовых входах (1/5) |
| type2 | LoRA `type2_mix10` | 4/5 | 1.386 | грамматический брак |
| **type2** | **LoRA `type2_mix20` + строгий v2-промпт (выбран)** | **5/5** | **1.388** | единственная конфигурация 5/5 без грамматического брака |

`type1_mix20` не завершил обучение (завис, снят) и исключён. v2-промпт для type2 (жёсткие два абзаца + лимит 450 знаков) выбран на validation до какой-либо финальной генерации.

**Почему LoRA, а не few-shot** (few-shot тоже дал 5/5 формата на validation): (1) стоимость на запрос — измеренный prefill ~867–937 промпт-токенов у few-shot против ~361–392 у LoRA+v2 на тех же входах (≈2.4× меньше, воспроизводится на 15 параллельных запросах); (2) устойчивость к длине — few-shot конструирует промпт из коротких обучающих примеров, что провоцирует рассогласование длины на длинных входах; конфигурация LoRA+строгий-промпт — единственная, прошедшая OOD-длинные тестовые входы без дословного копирования; (3) production — LoRA-адаптеры являются объектами первого класса в vLLM (`--lora-modules`), тогда как few-shot-шаблоны живут в коде приложения и дрейфуют. Few-shot остаётся документированным fallback без обучения; его validation-выводы сохранены в `outputs/orig/`.

Обучение (все прогоны): 5 эпох, ранняя остановка по val loss (patience 2), LR 7e-5 linear, batch 1 × grad-accum 4, seq len 1024, 8-bit AdamW, seed 42, BF16. Пики: 4.5–5.8 GiB зарезервировано на 8-гигабайтной ноутбучной GPU. Время прогона 460–1380 с.

## 4. Финальные результаты на тесте (5 постов × 2 стиля, id 1–5)

- Формат у сырой модели: **10/10** (0 обрезок, `hit_token_limit` нигде false); сданные файлы — это сырые выводы с прозрачными редакторскими правками, а НЕ скрытая постобработка.
- Редакторские правки: **5 из 10** постов, каждая восстанавливает/уточняет факты из источника (например, удалено выдуманное «до 150% больше» в type2 id=3; восстановлено разграничение штрафов 10/30 тыс. в type1 id=2; исправлен обрывок фразы в type2 id=5). Сырые выводы сохранены в `outputs/orig/`; каждая правка перечислена в `reports/final_outputs_audit.md` и `src/finalize_outputs.py`.
- Ручной факт-аудит (`reports/fact_audit_test.csv`): 0 `contradicted`, 0 `unsupported` в сданных текстах; оставшиеся флаги — принятые сокращения (лимит 450 знаков), каждое задокументировано с severity. Эвристические числовые дельты — только advisory, показаны отдельно.
- Сданные тексты: `outputs_type1.txt`, `outputs_type2.txt` — по пять постов, разделены нейтральным разделителем `———` (посты type2 содержат внутренние пустые строки, поэтому явный разделитель делает пять постов однозначно разделимыми); без id-маркеров, источников и модельных тегов.

## 6. Production-развёртывание (одна GPU 24 ГБ, ≤15 одновременных, ≤4096 контекст)

Команда-кандидат с валидацией (`deploy/vllm_24gb.sh`; статус: **кандидат, smoke-тест не выполнен — 24 ГБ GPU недоступно**):

```bash
python -m vllm.entrypoints.openai.api_server \
  --model unsloth/Qwen3.5-2B --dtype bfloat16 --tensor-parallel-size 1 \
  --max-model-len 4096 --max-num-seqs 15 --max-num-batched-tokens 4096 \
  --gpu-memory-utilization 0.85 --enable-lora --max-loras 2 --max-lora-rank 16 \
  --lora-modules type1=./adapters/type1 type2=./adapters/type2 \
  --host 0.0.0.0 --port 8000
```

Расчёт памяти по **верифицированному config.json** (`full_attention_interval=4` → 12 full-attention + 12 linear-attention слоёв, KV-головы 2 × head_dim 256): full-attention KV = 24,576 Б/токен → 15 × 4096 токенов = **1.41 GiB**; recurrent-состояния linear-attention ≈ 88 MiB; веса 4.24 GiB (измерено); LoRA ~42 MiB; с CUDA-графами и рабочими буферами ≈ **7.5–9 GiB в худшем случае** — с запасом внутри бюджета 20.4 GiB при `gpu_memory_utilization=0.85`. Защита от OOM: жёсткий лимит 4096 на последовательность (вход+выход, контроль на стороне приложения), `max_num_seqs=15` с очередью, и резервные рычаги (`--max-num-seqs`, `--max-num-batched-tokens`, `--enforce-eager`). Подробности: `deploy/production_memory.md`; скрипты: `deploy/smoke_test.py`, `deploy/load_test.py` (помечены NOT EXECUTED); контракт API: `deploy/api_examples.md`.

Совместимость vLLM/qwen3_5 (проверено 2026-10-27 по документации docs.vllm.ai): страница бэкбона есть в актуальных доках vLLM, LoRA работает через общий путь `SupportsLoRA`; тем не менее поддержка LoRA на гибридной архитектуре для точных target-модулей должна быть подтверждена smoke-тестом на 24 ГБ до production. Fallback при несовместимости: export/merge адаптеров или переобучение на Qwen2.5-3B-Instruct — задокументировано, не выдаётся за проверенное.

## 7. Ограничения

- Validation по 5 примерам на стиль → неопределённость выбора реальна; выбор дополнительно проверен чтением каждого вывода.
- Числовые проверки — эвристические (нормализованные) + ручная факт-таблица; regex-наборы advisory и содержат ложные срабатывания/пропуски.
- Нет LLM-judge и человеческой рубрик-оценки: независимый человек недоступен; только эвристики + ручной аудит, все пределы раскрыты.
- Тест-информированный выбор конфигурации (new_tokens 512→256) раскрыт выше.
- vLLM production-числа расчётные, не измеренные (`NOT EXECUTED`).
